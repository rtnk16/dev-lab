# AI ツールとワークフローの実践ガイド

このガイドでは、AI に適切な指示を与え、知識を渡し、ツールを接続して、繰り返し使えるワークフローを作る方法を説明します。製品によって、名称、対応機能、設定場所、指示の優先順位は異なります。設定例を適用する前に、利用する製品のドキュメントを確認してください。

## 1. 全体像

| 仕組み | 目的 | 例 |
| --- | --- | --- |
| Prompt（プロンプト） | 今回の作業を伝える | 特定の変更のレビューを依頼する |
| Instructions（指示） | 継続して適用するルールを定める | 動作を変更するときにテストを求める |
| Skill（スキル） | 再利用できる手順をまとめる | リリースのチェックリストに沿って進める |
| Context（コンテキスト） | 作業に必要な情報を渡す | 要件や関連コードを添付する |
| Memory（メモリ） | 選んだ情報をやり取りの間で保持する | 好みの文体を記憶する |
| Tool / Function Calling | 外部の操作を AI から要求する | ファイルを検索する、テストを実行する |
| MCP | ツールやデータへの接続を標準化する | 利用が承認された文書サービスに接続する |
| RAG | 回答の生成前に関連する知識を検索する | 社内文書に基づいて質問に答える |
| Agent（エージェント） | 目標に向けて一連の作業を進める | 変更を実装して検証する |
| Structured Output（構造化出力） | 回答の形式を制約する | スキーマに適合する JSON を返す |

これらの仕組みは組み合わせて使います。Instructions がルールを定め、Prompt が目標を伝え、Skill が手順を提供し、Tools が操作を担います。検索で関連するコンテキストを追加し、Agent が作業全体を調整します。

## 2. 効果的な Prompt の書き方

役立つプロンプトには、目的、関連する背景、制約、期待する出力、成功の判断基準を含めます。望む結果を言葉だけで説明しにくい場合は、例を示します。

```text
目的: 添付した API 案について、互換性のリスクをレビューしてください。
背景: 既存のクライアントは、現在のレスポンスのフィールドに依存しています。
制約: 提案を変更せず、文書化されていない動作を仮定しないでください。
出力: 指摘を重要度順に並べ、根拠と修正案を添えてください。
成功基準: 破壊的変更を特定し、不確かな点を明示すること。
```

作業を進めるために必要な情報から伝えます。大きな作業では、調査、実装、検証などの区切りを定めます。確認可能な根拠と、判断理由の簡潔な説明を求めましょう。

「これを改善して」という曖昧な依頼は、「この導入ページを初めて使う人向けに書き直し、技術的な要件を維持して、英語で 500 語以内にまとめてください」と具体化できます。修正を依頼するときは、元の依頼を繰り返すよりも、何が不足しているかを明示します。

## 3. Instructions の使い方

Instructions は、繰り返し適用するルールを記述したものです。製品によって、個人設定、ワークスペース設定、リポジトリ内のファイル、API メッセージなどに保存します。

言語や文体の好みは個人向けの指示に、アーキテクチャ、利用できるコマンド、コーディング規約、検証要件はプロジェクト向けの指示に記載します。一時的な要件は、その作業のプロンプトに含めます。

`AGENTS.md` を認識するコーディングエージェントもありますが、別のファイルを使ったり、明示的な設定を必要としたりする製品もあります。読み込みの規則、適用されるディレクトリの範囲、優先順位を製品のドキュメントで確認してください。ファイル名だけでは、内容が読み込まれる保証はありません。

プロジェクト向けの指示の例:

```markdown
# プロジェクトの指示

- 既存のアーキテクチャと命名規則に従う。
- 変更前に、関連するパッケージのドキュメントを読む。
- 既存の依存関係管理ツールとロックファイルを使う。
- 変更した動作に適した検証を実行する。
- 失敗した検証と未実行の検証を明示する。
- コード、ログ、ドキュメントに認証情報を含めない。
```

ルールは短く、実行可能で、互いに矛盾しない内容にします。古くなったルールは削除します。指示が競合した場合は、利用するホストの指示階層を確認し、未解決のプロジェクト要件を明確にします。最後に書かれた文章が常に優先されるとは限りません。

## 4. Skills の作り方と使い方

Skill は、繰り返す作業の指示と、対応している場合はスクリプト、テンプレート、参考資料をまとめたものです。リリース準備、環境構築、インシデントの初期調査、ドキュメントレビューなどに向いています。

`SKILL.md` に対応するプラットフォームでは、次のような構成が使われます。ただし、メタデータや読み込みの要件は製品ごとに異なります。

```text
documentation-review/
  SKILL.md
  references/style-guide.md
  scripts/check-links.sh
  templates/review.md
```

Skill には、利用する場面、前提条件、手順、検証方法、失敗時の対応、期待する出力を記載します。どの操作に承認が必要かも明示します。シークレットは Skill の外で管理してください。

```markdown
# ドキュメントレビュー

プロジェクトのドキュメントをレビューするときに使用する。

1. 読者と変更されたページを確認する。
2. プロジェクトのスタイルガイドを読む。
3. 例、リンク、現在の動作との整合性を確認する。
4. 利用可能なドキュメントの検証を実行する。
5. ファイルへの参照と検証結果を添えて指摘を報告する。
```

ホストが対応する方法で Skill を呼び出し、読み込まれたことを確認します。運用に使う前に、代表的な作業で試してください。対象のワークフローとともにバージョン管理し、コマンドや方針が変わったら更新します。

## 5. Context と Memory の管理

Context は、現在の回答に利用できる情報です。メッセージ、ファイル、検索された文章、ツールの結果、システムから提供された情報などが含まれます。コンテキストウィンドウには上限があるため、長い会話は一部が省略されたり、要約されたりする場合があります。

関連ファイル、現在の要件、正確なエラー、最近の決定事項など、必要な資料を絞って渡します。鮮度が重要な情報には、出典と日付を付けます。無関係なリポジトリやログを大量に会話へ投入することは避けます。

Memory は、製品と設定に応じて、選んだ好みや事実を会話をまたいで保持することがあります。バージョン管理されたプロジェクト文書の代わりとして頼ることはできません。対応する管理機能で、保存情報を確認、修正、削除してください。

長い作業では、目的、合意した決定事項、完了した作業、残りの手順、検証状況を短い引き継ぎメモにまとめます。変化する事実は再確認し、古い会話履歴を現在の証拠として扱わないようにします。

## 6. Tools・Function Calling・MCP

Tools を使うと、AI はファイルの読み取り、検索、コマンド実行、API 呼び出しなどの操作を要求できます。Function Calling では、アプリケーションが名前付きの操作と引数のスキーマを公開します。モデルが呼び出しを提案し、ホストが権限に従って検証・実行します。呼び出しの提案だけでは、実行された証拠にはなりません。

Model Context Protocol（MCP）は、AI アプリケーションと外部機能の通信を標準化するプロトコルです。ホストは MCP クライアントを通じて接続を管理し、サーバーは対応する機能を公開します。MCP 自体がアクセス権を与えたり、サービスの信頼性を保証したりするわけではありません。

| MCP の機能 | 主な用途 |
| --- | --- |
| Tools | 検索や Issue の作成などの操作を実行する |
| Resources | 識別可能なリソースとしてデータを公開する |
| Prompts | 再利用できるメッセージのテンプレートを提供する |

クライアントごとに対応状況は異なり、サーバーもすべての機能を実装する必要はありません。MCP の Prompt はサーバーが公開するテンプレートであり、作業手順全体をまとめる Skill とは異なります。

サーバーへの接続手順:

1. 信頼できるサーバーを選び、対応する通信方式と機能を確認する。
2. ホストのドキュメントに従って設定する。
3. 承認されたシークレット保管機能や認可フローで認証する。
4. 読み取り専用から始め、必要最小限の権限を付与する。
5. 影響のない操作を試し、返された結果を確認する。
6. 必要性と権限が確認できた場合にのみ、書き込み操作を有効にする。

接続に失敗したときは、サーバーの起動エラー、通信の問題、未対応の機能、認証の期限切れ、権限不足を区別します。トークンを露出させず、機密情報を除いたログを調べてください。同じ目的を達成できるなら、無制限のコマンド実行よりも、引数が明確で機能が限定されたツールを優先します。

## 7. 検索・RAG・ナレッジソース

Retrieval-Augmented Generation（RAG、検索拡張生成）は、知識ソースを検索し、関連する結果をモデルに渡してから回答を生成する方法です。一般的には、文書の取り込み、文章の分割、インデックス作成、候補の検索、根拠への参照を含む回答の生成という流れになります。

作業に必要な少量の資料にはファイル添付を使います。最新情報や広く分散した情報には検索を使います。継続的に管理され、多くの質問に繰り返し使う資料群には RAG を検討します。MCP で検索サービスを公開することもできますが、MCP と RAG はワークフローの異なる部分を担います。

文書の所有者、アクセス制御、出典の識別情報、更新日を維持します。検索時点で、質問するユーザーのアクセス権を適用する必要があります。最終回答だけをフィルタリングしても十分ではありません。

正しい文章が検索されたか、回答がその文章に裏付けられているかを評価します。出典の提示を求め、実際の主張を支えているか確認してください。情報が不足していたり、資料同士が矛盾していたりする場合は、根拠のない回答で埋めずに、その不足を報告します。

## 8. Agent・Sub-agent・Workflow

Agent は、目標、コンテキスト、ツール、制御ループを組み合わせて複数の手順を実行します。基本的な流れは、状況を調べ、操作を選び、実行し、結果を評価して、継続するか終了するかを決めることです。

大きな作業を任せる前に、範囲、利用できるツール、成功基準、リソースの上限、停止条件を定めます。公開、支出、本番データの変更など、影響の大きい操作には確認の段階を設けます。

Sub-agent は、別々のモジュールのレビューなど、独立した作業を担当できます。それぞれに明確な担当と期待する結果を伝えます。ファイルやサービスの共有は競合を生むことがあるため、担当範囲を定め、統合した結果を確認してください。エージェントを増やすと調整コストも増え、品質が自動的に上がるわけではありません。

安定した処理順序には決められたワークフローを使い、解釈が必要な部分にエージェントの判断を使います。定期実行やイベントを起点とする自動化にも、明確な認証設定、再試行、重複操作の防止、ログ、失敗通知が必要です。

中断後に再開できるよう、進捗をファイルや承認された状態保存先に記録します。成功の報告は、ツールの結果や生成物と照合して検証する対象として扱います。

## 9. 出力形式と品質評価

人が読む説明には Markdown、比較には表、後続のソフトウェアが処理する情報には構造化データを選びます。一定のレイアウトが重要な場合は、テンプレートを提供します。

JSON を求めるだけでは、構文が正しい出力やスキーマへの適合は保証されません。対応している場合は、スキーマを指定した構造化出力を使い、利用側のアプリケーションで結果を検証します。形式が正しくても、内容まで正しいとは限りません。

```json
{
  "summary": "確認した結果を記載する",
  "findings": [
    {
      "severity": "medium",
      "evidence": "確認した出典への参照",
      "recommendation": "具体的な次の操作"
    }
  ],
  "validation_status": "not_run"
}
```

評価（Evals）は、代表的な作業、期待する性質、既知の失敗例をもとに作ります。事実の裏付け、作業の完了、権限の順守、テスト結果、応答時間、コストなどが評価基準になります。自動採点では信頼できる判断ができない部分には、人によるレビューを使います。

モデル、プロンプト、Skill は同じ例で比較します。品質の後退を追跡し、過度な最適化を防ぐため、調整には使わない評価用の事例も確保します。成功、失敗、スキップ、未実行を区別してください。実測した品質、応答時間、必要なコンテキスト量、コストに基づいてモデルを選びます。

## 10. 安全な運用

認証情報は承認されたシークレット保管先で管理し、プロンプト、リポジトリ、ログにコピーしないようにします。作業に必要な情報だけを共有し、サービスの保存期間やデータ利用の設定を確認してください。

プロンプトインジェクションは、信頼できないコンテンツが AI の動作を変更しようとする攻撃です。検索された文書、Web サイト、リポジトリ内のファイル、ツールの応答に、そのような指示が含まれる場合があります。それらをデータとして扱い、要求が許可された作業に合致するか確認し、新たな権限を与える根拠にしないでください。

サンドボックス、限定されたファイルアクセス、接続先の制限、最小権限の認証情報を使います。読み取りと影響の大きい操作を分け、必要に応じてホストの承認機能を利用します。コマンドの引数や構造化された入力は、アプリケーションのコードでも検証します。

外部への書き込みや公開の前には、操作先、範囲、内容、権限、復旧方法を確認します。シークレットを記録せず、役立つ監査記録を残してください。生成コード、事実に関する主張、ライセンス、利用権は、作業の要件に応じて確認します。

## 11. 実践的なワークフロー

### Instructions でプロジェクトのルールを共有する

ホストが対応するプロジェクト指示ファイルを作り、リポジトリの規約と実際に使う検証コマンドを記載します。小さな作業を依頼し、エージェントがそのファイルを読み込んで従うことを確認します。作業固有の例外は明示します。

### ドキュメントレビューの Skill を再利用する

レビュー手順、スタイルの参考資料、既存のリンクチェッカーを Skill にまとめます。変更されたページに対して呼び出し、チェッカーが実際に実行されたことを確認して、指摘を元の文書と照合します。

### MCP で外部の情報を読む

承認された課題管理サーバーに読み取り専用で接続します。返された根拠を使って、指定した Issue の要約を AI に依頼します。Issue の更新を有効にする前に、識別子と出典のリンクを確認します。

### RAG で質問に答える

管理されている文書群を、権限のメタデータとともにインデックス化します。質問に関連する文章を検索し、出典付きの回答を生成して、元の資料と照合します。資料に答えが含まれていないケースも評価に含めます。

### Agent で実装と検証を進める

具体的な動作の変更、リポジトリのルール、受け入れ基準をエージェントに渡します。コードを調査し、範囲を絞った変更を行い、関連するテストを実行させます。マージやデプロイの前に、差分と実際のテスト出力をレビューします。

### 仕組みを組み合わせる

繰り返し行うサポート業務では、Instructions が対話とプライバシーのルールを定め、Skill が初期調査の手順を示し、検索が製品知識を提供し、MCP ツールが関連チケットを読み取ります。エージェントがそれらの手順を調整し、構造化された下書きを返します。影響の大きい外部への操作は、組織の方針に従って人がレビューします。

まず一つの役立つワークフローから始め、実際の例で検証し、確認できた課題の解決に必要な場合にだけ仕組みを追加します。
